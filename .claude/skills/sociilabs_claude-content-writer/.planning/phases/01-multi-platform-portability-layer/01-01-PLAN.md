  <action>
    Create skills/state-schema.md with four sections, in this order:

    (1) "Profile Schema" — table of the four profile files under
    content-writer-output/profile/ and, for each, its required structure: PROFILE.md must contain
    these exact headings in order: "# Writer Profile", "## Identity", "## Audience", "## Voice",
    "## Content Strategy", "## Publishing". PRODUCTS.md: one "### [product name]" subsection per
    product with fields description, target_customer, key_benefit, price_range, use_when.
    CTAS.md: one "### [label]" subsection per CTA with fields type, copy, platforms, url.
    CASE-STUDIES.md: one "### [label]" subsection per case study with fields client_context,
    problem, approach, outcome, nda_status, rotation (rotation is one of active, rest, retired).

    (2) "Project State Schema" — defines content-writer-output/profile/PROJECT-STATE.md as a
    single file with YAML frontmatter followed by a markdown body. State explicitly: frontmatter
    keys are flat `key: value` pairs only — no nested maps, no multiline blocks, lists are
    inline comma-separated strings — so the file stays parseable by a plain regex/string-split
    check instead of a full YAML parser. List the frontmatter keys in this exact order and name:
    phase, platform, format, topic, angle, audience, awareness_stage, goal, framework, length,
    cta, research_urls, key_points, seo_primary_keyword, seo_secondary_keywords, seo_meta_title,
    seo_meta_description, seo_slug, platform_conventions_file, voice_notes, proof_points,
    cta_placement, draft_word_count, cta_expanded, seo_score, ai_patterns_fixed, manual_check,
    updated_at. Document the four required markdown body headings that follow the frontmatter,
    in order: "## Discussion Brief", "## Outline", "## Draft", "## Verified Content" — each holds
    the long-form text produced by the matching phase (kept out of frontmatter since it's
    long-form prose, not a flat key/value).

    (3) "Phase State Machine" — a table mapping the `phase` frontmatter value to the command that
    should run next, replacing key-presence detection with field-value detection: no
    PROJECT-STATE.md file exists -> run /writer:discuss; phase: discuss -> run /writer:plan;
    phase: plan -> run /writer:execute; phase: execute -> run /writer:verify; phase: verify ->
    run /writer:ship; phase: ship or phase: complete -> workflow finished, run /writer:discuss
    for a new project. State explicitly that this table is what every adapter (Claude Code,
    Claude.ai, ChatGPT, Gemini, headless/MCP) uses for phase detection — nothing else is needed.

    (4) "File-First Storage Rule" — state explicitly, as the load-bearing rule for the whole
    phase: the project-state file and the four profile files are the sole source of truth on
    every platform. A keyed session-storage mechanism (Claude Code's memory tool, or any chat
    platform's own opaque per-account memory feature) may be used as an optional read-through
    cache repopulated FROM these files on load, but is never authoritative and is never the only
    place a value lives. On platforms with no persistent storage between sessions (ChatGPT,
    Gemini), the adapter must output the full updated PROJECT-STATE.md content as chat text at
    the end of every phase, instructing the user to save or re-paste it next session — it must
    never claim to have saved the file on the user's behalf.
  </action>
